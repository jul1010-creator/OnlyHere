His words: "It shouldn't be difficult to make a route…" The map was not making a route, it was joining dots.

Each leg is drawn separately with its own real mode, resolved by the same `resolveLegMode` call and same-town-walk override the leg chip already uses, because a ferry crossing and a walk between two points are different journeys. Where no real route comes back, the leg keeps its dashed straight line, which reads as "roughly this way" instead of pretending to be a road. Legs whose stops collapsed to one point are skipped rather than fetched, since that is the town-centre collapse behind the old "1 min walk that was really 30" bug. Bounds now fit what is actually drawn, because a real route can swing outside the box its endpoints make and fitting to the markers would crop the part that explains the journey.

# HOTFIX (right after LATEST 7): found and fixed a total-app-crash bug, live in production — "ReferenceError: guideModal is not defined"

**You pasted a real production console error right after this pass's summary: `ReferenceError: guideModal is not defined`, caught by the top-level ErrorBoundary.** This was NOT something introduced by tonight's work — it's a real, pre-existing bug that's been sitting in the code since at least PASS 21 (whenever the `liveGuide` prop was first wired up), just never actually hit in a real deployed build until now.

**Root cause, confirmed with a real scope-check, not a guess:** `src/App.jsx` has TWO separate top-level components — `function GemlyxApp()` (everything: home, chat, Studio, guideModal state, all of it) and, way below it, `export default function Gemlyx()` (a thin wrapper that just renders `<Routes>`). The `/guide/new` route read `<Route path="/guide/new" element={<GuidePage liveGuide={guideModal} />} />` — but `guideModal` is state declared INSIDE `GemlyxApp`, and `Gemlyx()` is a totally separate function with no access to it. That's a bare reference to an identifier that doesn't exist in scope: a hard ReferenceError. Since a `<Route>`'s `element` JSX gets constructed the instant `<Routes>` itself renders (regardless of which path is actually active), this crashed on EVERY single page load, not just when visiting a guide — the entire app, always. I confirmed this precisely (not just by reading it) by minifying `App.jsx` with esbuild and checking which identifiers survived minification: a properly-scoped local variable gets renamed consistently everywhere it's used, but this one specific `guideModal` reference was the ONLY one of ~20 occurrences that stayed un-renamed, proof it wasn't resolving to the real state variable at all.

**Why this was never actually working code to begin with, crash or no crash:** `GemlyxApp` is only mounted at path "/" — React Router unmounts it the instant you navigate to "/guide/new". So even if `guideModal` had somehow been in scope, the whole point of passing it (letting weather/exact-duration background updates keep patching into the guide page after navigation) could never have worked, since the component holding that state dies the moment you leave "/". This wasn't a working feature that broke, it was never reachable.

**Fix**: removed the broken `liveGuide={guideModal}` prop from that Route entirely. `GuidePage` already gets the freshly-built guide correctly through router state (`navigate("/guide/new", { state: { guide: guideModal } })`, set BEFORE navigation, nothing to do with the wrapper's scope) — so the actual guide-display behavior is unaffected, only the (never-functional) "keeps live-patching after navigation" idea is gone.
