## HOTFIX, Aug 4 2026, PASS 24: a total-app-crash bug was found and fixed — read this before trusting "esbuild-clean" as proof of anything
Oliver hit a real production crash right after PASS 24 was reported done: `ReferenceError: guideModal is not defined`, caught by the ErrorBoundary, on every single page load. Root cause: App.jsx has two separate top-level components — `function GemlyxApp()` (all the real state, including `guideModal`) and, far below it, `export default function Gemlyx()` (a thin `<Routes>` wrapper, the actual default export). The `/guide/new` route read `element={<GuidePage liveGuide={guideModal} />}`, but `guideModal` only exists inside `GemlyxApp`'s own closure, not `Gemlyx()`'s — a bare out-of-scope reference. Since a `<Route>`'s `element` JSX is constructed the instant `<Routes>` itself renders, this crashed literally every page load, not just guide pages. This was a PRE-EXISTING bug (likely dormant since around PASS 21, whenever `liveGuide` was first wired up) — nothing in PASS 24's own new work touched this line — it just never got hit in an actual deployed build until now. Fixed by removing the broken `liveGuide={guideModal}` prop; `GuidePage` still gets the guide correctly via router state (`navigate("/guide/new", { state: { guide: guideModal } })`), which was always independent of this bug. Worth knowing: even without the crash, that prop could never have worked anyway, since `GemlyxApp` unmounts the instant you navigate away from "/", so the "keep live-patching weather/durations into the guide after navigation" idea behind it was unreachable by design.

**New verification technique worth adopting going forward**: plain esbuild syntax checks (used throughout this project's history) cannot catch a bare identifier referenced across two sibling top-level components — that's syntactically valid JS, it only breaks at runtime. Confirmed this bug precisely (not by guessing) with a fast alternative: run `esbuild --minify` on the file and check whether a suspect identifier still appears literally in the output. A properly in-scope local variable gets renamed consistently everywhere by the minifier; one that survives un-renamed isn't resolving where you think it is. Worth running as a standard extra check any time a file has more than one top-level component, especially around a Routes/wrapper boundary — "esbuild compiles clean" has never meant "this runs correctly," and this is a concrete example of exactly how that gap bites.

## Known architecture footgun: the tab pager breaks `position: fixed`
Every page (Home/Towns/Events/Food/Nightlife/etc) renders inside a shared strip (`stripRef` in App.jsx's PAGER) that uses `transform: translateX(...)` for the swipe animation. CSS spec: a transform on an ancestor becomes the containing block for any `position: fixed` descendant, so ANY fixed-position modal/sheet rendered as part of a tab's own content (not the top-level return, which sits outside the strip and is safe) will anchor to that giant multi-tab strip instead of the real screen and get clipped to a corner sliver. This is what caused "you click the filters and they jump to the corner." Fixed so far, via `createPortal(..., document.body)`: FilterChip's sheet (App.jsx), WeatherHeaderStrip's city popup. If a new fixed-position overlay gets added to any page's own content (not the modals already living at the bottom of GemlyxApp's return, past the PAGER close), it needs the same portal treatment or it WILL have this bug, even if it looks fine in isolation during dev.
